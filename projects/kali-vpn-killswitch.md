# Kali Linux Fail-Closed VPN Environment

## Overview

This project documents the configuration of a fail-closed Kali Linux virtual machine using Mullvad VPN, WireGuard, and nftables. The environment was designed to prevent outbound network traffic from bypassing the VPN tunnel, applying security principles such as least privilege, default deny, network isolation, and egress filtering.

## Objective

The objective of this project is to configure a Kali Linux virtual machine so that all regular Internet-bound traffic is forced through the VPN tunnel.

The environment must prevent the virtual machine from communicating through the underlying network interface if the VPN connection becomes unavailable, reducing the risk of traffic leaks and unintended network exposure.

## Threat Model

### Assets
The primary assets protected by this project are the confidentiality of the virtual machine's outbound network traffic and the network information that could expose the user's underlying connection.

This includes the public IP address associated with the host network, outbound traffic generated by the virtual machine, and network requests that could reveal activity if they were transmitted outside the VPN tunnel.

The project is focused on protecting network exposure rather than the confidentiality of files or data stored locally inside the virtual machine.

### Threats

Considering the assets listed above, several threats could compromise one or more of them.

- **VPN tunnel failure:** The WireGuard tunnel could become unavailable or unstable. Without proper fail-closed controls, outbound traffic could then be transmitted through the underlying network interface, exposing the host's public IP address and network activity.

- **Fallback to the default route:** If the VPN tunnel becomes unavailable, the operating system could fall back to its default network route and send traffic through the regular network interface.

- **Firewall misconfiguration:** Incorrect, incomplete, or missing nftables rules could unintentionally allow outbound traffic to bypass the VPN tunnel. Other configuration errors could also prevent the VPN from establishing a connection, affecting availability.

- **Unintended interface exposure:** Outbound traffic could be transmitted through an interface other than `wg-mullvad`, bypassing the intended VPN path and exposing the underlying connection.

### Trust Boundaries

The level of trust changes primarily at four points within the architecture:

- **Kali VM → nftables:** The virtual machine generates network traffic, while nftables enforces the rules that determine which packets are allowed to leave the system.

- **Kali networking → WireGuard tunnel:** Traffic permitted by the firewall is expected to be routed through the WireGuard interface, `wg-mullvad`.

- **Virtual machine → host/VirtualBox network:** The virtual machine depends on the host's network infrastructure to reach the VPN endpoint. However, it must not be allowed to use this underlying network path to freely access the Internet outside the VPN tunnel.

- **Mullvad endpoint → public Internet:** Once the encrypted traffic reaches the Mullvad VPN endpoint, the VPN tunnel terminates and Mullvad forwards the traffic to the public Internet. From this point onward, the traffic is outside the direct control of the virtual machine.

### Security Controls

- **Default-deny outbound policy:** By default, all outbound network traffic is blocked unless it is explicitly allowed by the firewall rules.

- **WireGuard-only outbound traffic:** Regular outbound traffic is only permitted through the WireGuard interface, `wg-mullvad`, preventing applications from using the underlying network path directly.

- **VPN endpoint exception:** The underlying network interface is allowed to communicate only with the specific Mullvad VPN endpoint required to establish and maintain the WireGuard tunnel. This exception prevents unrestricted Internet access through the default network path.

- **Loopback exception:** Traffic through the loopback interface (`lo`) is always permitted, allowing local processes to communicate with services running on the same system.

- **Configuration validation:** After the configuration is applied, the active nftables ruleset, the WireGuard interface, and the tunnel status are verified to confirm that the expected security controls are in place.

- **Fail-closed behavior:** To reduce the risk of traffic leaks, the environment follows a fail-closed design. If the VPN tunnel becomes unavailable, the virtual machine loses external network connectivity instead of falling back to the default network route.

### Assumptions

The security model implemented in this project relies on the following assumptions:

- **Trusted host system:** The host operating system is assumed to be uncompromised and operating as expected.

- **Trusted virtualization layer:** VirtualBox is assumed to correctly isolate the guest operating system and provide the expected virtual network interface.

- **Trusted VPN provider:** Mullvad and its VPN infrastructure are treated as trusted components within the scope of this project.

- **Firewall integrity:** nftables rules are assumed to be correctly loaded and not modified by unauthorized processes or users.

- **WireGuard integrity:** The `wg-mullvad` interface is assumed to represent the intended WireGuard tunnel configured with the expected Mullvad endpoint.

- **Administrative control:** It is assumed that users with sufficient privileges will not intentionally disable or modify the security controls implemented by the project.


### Out of Scope

The following scenarios are outside the scope of this project:

- **Host compromise:** If the host operating system is compromised, this project cannot guarantee the protection of the virtual machine or its network traffic.

- **VirtualBox vulnerabilities:** This project does not provide protection against vulnerabilities affecting VirtualBox or the underlying virtualization layer.

- **Virtual machine compromise:** This project does not protect the virtual machine against malware or an attacker who has already obtained sufficient privileges inside the guest operating system.

- **Data-at-rest protection:** Data stored locally inside the virtual machine is not protected by the network controls implemented in this project.

- **Network and infrastructure attacks:** Attacks against the router, ISP, physical host, or other external infrastructure are not addressed by this project.

- **Anonymity guarantees:** This project reduces the risk of unintended traffic exposure outside the VPN tunnel, but it does not guarantee anonymity.

- **VPN provider security:** The security and integrity of Mullvad's infrastructure are outside the scope of this project. Mullvad is treated as a trusted component within the threat model.

- **Application-level tracking:** This project does not protect against application-level tracking mechanisms such as cookies, browser fingerprinting, authenticated accounts, or other application-specific identifiers.

## Environment

- **Host operating system:** Windows 11 (64-bit)

- **Virtualization platform:** Oracle VirtualBox

- **Guest operating system:** Kali Linux

- **Virtual network adapter:** Intel PRO/1000 MT Desktop

- **Virtual network mode:** NAT

- **Guest network interface:** `eth0`

- **VPN provider:** Mullvad VPN

- **VPN protocol:** WireGuard

- **VPN interface:** `wg-mullvad`

- **Firewall framework:** nftables

## Architecture

The following flow describes the simplified architecture used by regular Internet-bound traffic generated inside the Kali Linux virtual machine and routed through the Mullvad VPN tunnel.

- **Application inside the Kali VM:** An application running inside Kali Linux generates network traffic intended for a destination on the Internet.

- **Kali routing decision:** The Linux kernel evaluates its routing rules and determines which network path and interface should be used to reach the destination.

- **nftables:** The firewall evaluates the traffic according to the configured rules. If the traffic does not match an allowed path, it is dropped. nftables does not determine the route itself; it enforces whether the selected network path is permitted.

- **`wg-mullvad`:** When regular Internet-bound traffic is routed through the WireGuard interface and permitted by the firewall, WireGuard encapsulates and encrypts the original packet. The original destination remains inside the encrypted payload, while a new outer packet is created with the Mullvad VPN endpoint as its destination.

- **`eth0`:** The `wg-mullvad` interface is a logical interface and does not provide physical connectivity by itself. The encrypted WireGuard packet therefore uses Kali's `eth0` interface to reach the underlying VirtualBox network.

- **VirtualBox NAT:** The VirtualBox NAT layer provides the guest machine with access to the host's network connectivity, performing the necessary address translation between the virtual machine and the external network.

- **Windows host:** The host operating system provides the physical network connectivity used by VirtualBox. The encrypted packet is transmitted through the host's physical network interface, such as Ethernet or Wi-Fi.

- **ISP:** The Internet Service Provider can observe that the host's public connection is communicating with a Mullvad VPN endpoint. However, the ISP cannot directly inspect the original packet contents or directly determine the final Internet destination from the encrypted tunnel payload.

- **Mullvad VPN endpoint:** The WireGuard tunnel terminates at the Mullvad VPN server. The outer WireGuard packet is decrypted and decapsulated, recovering the original packet and its destination. Mullvad then forwards that traffic to the public Internet, where it continues toward the intended destination.

### Network Flow

![Network Flow](/assets/images/kali-vpn-killswitch/network-flow-diagram.png)

Under normal conditions, Internet-bound traffic generated inside the Kali virtual machine is routed through the WireGuard interface, encrypted, transmitted through the underlying `eth0` path, and delivered to the Mullvad VPN endpoint before reaching the public Internet.

### Fail-Closed Flow

![Fail-Closed Flow](/assets/images/kali-vpn-killswitch/fail-closed-flow-diagram.png)

If the VPN tunnel becomes unavailable, nftables prevents regular outbound traffic from using the underlying `eth0` path directly. As a result, the virtual machine loses external connectivity instead of leaking traffic outside the VPN tunnel.

## Implementation

### Virtual Machine Setup

The project was built on a Kali Linux virtual machine running inside Oracle VirtualBox on a Windows 11 host.

The virtual machine was configured with a NAT-based network adapter using the Intel PRO/1000 MT Desktop virtual adapter. This setup provided the guest system with underlying network connectivity through the `eth0` interface, while preserving network separation between the guest and the host environment.

This configuration was sufficient for the project because the goal was not to expose the guest directly to the local network, but to provide controlled outbound connectivity that could later be restricted through WireGuard and nftables.



### WireGuard

The VPN tunnel was configured using WireGuard with a Mullvad VPN server acting as the remote peer. The configuration is stored in `/etc/wireguard/wg-mullvad.conf` and loaded through `wg-quick`.

The relevant configuration follows the structure below. Sensitive and environment-specific values are omitted from the public documentation.

![Sanitized WireGuard configuration](/assets/images/kali-vpn-killswitch/wireguard-configuration.png)

The `[Interface]` section defines the local side of the WireGuard tunnel.

The `[Peer]` section defines the remote Mullvad WireGuard peer. The `AllowedIPs` value is configured as `0.0.0.0/0`, associating all IPv4 destinations with this peer and allowing regular IPv4 Internet traffic to be routed through the VPN tunnel.

When the configuration is activated through `wg-quick`, additional networking configuration is automatically created by the system. This includes the `wg-mullvad` interface, a dedicated routing table, routing policy rules, a firewall mark, and auxiliary nftables rules required by the WireGuard routing mechanism.

The service responsible for loading the WireGuard configuration is managed by systemd and is enabled to start automatically during system boot.

![WireGuard systemd service](/assets/images/kali-vpn-killswitch/wireguard-systemd-service.png)

Because the WireGuard peer handles the IPv4 default route, `wg-quick` creates a dedicated routing table instead of simply replacing the default route in the main routing table.

Regular Internet-bound IPv4 packets that are not handled by more specific routes are directed to routing table `51820`, whose default route uses the `wg-mullvad` interface.

![WireGuard policy routing](/assets/images/kali-vpn-killswitch/wireguard-policy-routing.png)

After a packet enters `wg-mullvad`, WireGuard encrypts and encapsulates the original packet inside a new UDP packet addressed to the Mullvad VPN endpoint.

The resulting outer WireGuard packet receives the firewall mark `0xca6c` (`51820` in decimal).

This mark prevents the encrypted packet from being routed back into the VPN tunnel, which would create a routing loop.

Instead, the marked WireGuard packet bypasses routing table `51820` and uses the main routing table, allowing it to leave the virtual machine through `eth0`, reach the VirtualBox NAT gateway, and ultimately communicate with the Mullvad VPN endpoint.

This separation between inner VPN traffic and outer encrypted WireGuard traffic allows normal Internet traffic to remain inside the VPN tunnel while still permitting the tunnel itself to use the underlying network connection.

### nftables

The fail-closed firewall was implemented using nftables through a dedicated `inet` table named `killswitch`.

Using the `inet` family allows the same filtering policy to apply to both Ipv4 and Ipv6 traffic.

The main outbound chain uses a default-drop policy. This means that outbound traffic is denied unless it matches an explicitly permitted rule.

![nftables kill switch ruleset](/assets/images/kali-vpn-killswitch/nftables-killswitch-ruleset.png)

The outbound policy allows only the traffic required for the environment to operate correctly:

- Traffic through the loopback interface is permitted for local process communication.
- Established and related connections are accepted through connection tracking.
- Regular outbound traffic is permitted when the selected output interface is `wg-mullvad`.
- Direct communication through the underlying network is restricted to the Mullvad WireGuard endpoint over UDP port `51820`, allowing the VPN tunnel itself to be established and maintained.
- DHCP client traffic is allowed so that the virtual machine can obtain and renew its network configuration.

All other outbound traffic is denied by the chain's default-drop policy.

The input chain remains permissive because inbound host hardening is outside the primary scope of this project. The forward chain uses a default-drop policy to prevent the virtual machine from freely forwarding traffic between interfaces.

A separate nftables table named `wg-quick-wg-mullvad` is created automatically by `wg-quick`. These rules support the WireGuard policy-routing mechanism and are distinct from the custom `killswitch` table implemented for this project.


### Kill Switch Logic

The kill switch follows a fail-closed design: outbound network access is denied by default and is only permitted through explicitly authorized paths.

During normal operation, regular IPv4 traffic is routed through the `wg-mullvad` interface. Because outbound traffic through this interface is explicitly allowed by the firewall, applications can communicate with the Internet through the VPN tunnel.

WireGuard then encrypts and encapsulates this traffic into UDP packets addressed to the Mullvad VPN endpoint. These outer packets must use the underlying `eth0` interface to reach the VPN server. For this reason, the firewall contains a narrowly scoped exception that permits direct communication only with the configured Mullvad endpoint over UDP port `51820`.

The resulting behavior separates regular application traffic from the traffic required to maintain the VPN tunnel:

- Regular Internet traffic is allowed through `wg-mullvad`.
- Direct Internet traffic through `eth0` is denied.
- Communication through `eth0` is permitted only when required to reach the Mullvad WireGuard endpoint or maintain the virtual machine's network configuration.

If the VPN tunnel becomes unavailable, regular traffic can no longer rely on `wg-mullvad`. Even if the operating system attempts to use the underlying default route through `eth0`, the firewall does not permit unrestricted outbound traffic through that interface.

As a result, loss of the VPN tunnel results in loss of external connectivity rather than fallback to the host's regular Internet connection.

The same default-deny behavior also applies to IPv6. The WireGuard configuration used in this project routes IPv4 through the VPN but does not define an IPv6 default route through the peer. Although the virtual machine has an IPv6 default route through `eth0`, the `inet` nftables kill switch applies to both IPv4 and IPv6 and does not authorize regular IPv6 traffic through the underlying interface.

The intended fail-closed behavior can therefore be summarized as:

**VPN available:** regular traffic is routed through `wg-mullvad` and permitted.

**VPN unavailable:** regular traffic attempting to use `eth0` is denied.

**Direct IPv6 traffic:** traffic attempting to use the IPv6 default route through `eth0` is denied.

**VPN establishment:** UDP traffic to the configured Mullvad endpoint remains permitted so that the WireGuard tunnel can be established and maintained.

This design ensures that the existence of an underlying network route does not automatically imply permission to use it. Linux routing determines where a packet should go, while nftables independently enforces whether that network path is authorized.

### Configuration Persistence

Both the nftables kill switch and the WireGuard tunnel are configured to persist across system reboots through systemd services.

The nftables service is enabled at boot and loads the firewall configuration from `/etc/nftables.conf`.

![nftables persistence](/assets/images/kali-vpn-killswitch/nftables-persistence.png)

This file contains the custom `inet killswitch` table and applies a default-drop outbound policy before the system reaches the normal network initialization stage.

![Persistent nftables configuration](/assets/images/kali-vpn-killswitch/nftables-conf.png)

The nftables service is ordered before `network-pre.target`, which causes the firewall rules to be loaded early during the boot process.

This is important for the fail-closed design because the underlying network interface may become available before the VPN tunnel is established. By loading the firewall first, unrestricted outbound traffic through `eth0` remains blocked during this transition.

The WireGuard configuration is managed by the `wg-quick@wg-mullvad` systemd service, which is also enabled at boot.

Unlike nftables, the WireGuard service is ordered after `network-online.target`. This allows the underlying network connection to become available before `wg-quick` attempts to establish the VPN tunnel.

![WireGuard and nftables boot ordering](/assets/images/kali-vpn-killswitch/boot-ordering.png)

During a normal boot, the resulting initialization sequence is:

1. nftables loads the fail-closed firewall policy.
2. The underlying network configuration becomes available.
3. `wg-quick` creates the `wg-mullvad` interface and configures the WireGuard tunnel.
4. `wg-quick` adds its policy-routing rules, routing table, firewall mark, and auxiliary nftables rules.
5. Regular outbound traffic becomes available through the VPN tunnel.

This ordering also prevents the `flush ruleset` directive in `/etc/nftables.conf` from removing the nftables rules automatically created by `wg-quick` during normal system startup, since the WireGuard-specific rules are added only after the persistent nftables configuration has already been loaded.

The resulting boot behavior preserves the fail-closed model: the firewall becomes active before the VPN is available, and external connectivity is only restored once traffic can use the authorized WireGuard path.

## Validation

The environment was validated through a series of controlled tests designed to verify VPN connectivity, fail-closed behavior, IPv6 leak prevention, and DNS leak prevention.

The objective of these tests was not only to confirm that the VPN worked during normal operation, but also to verify how the environment behaved when alternative network paths were available or when the VPN tunnel became unavailable.

### VPN Tunnel Connectivity

The first test established a baseline with the WireGuard tunnel operating normally.

The `wg-mullvad` interface was active, a recent WireGuard handshake was observed, and transfer counters confirmed communication with the Mullvad peer.

An IPv4 HTTPS request was then performed successfully, returning an HTTP `200` response. The connection used the IPv4 address assigned to the `wg-mullvad` interface as its local source address.

This confirmed that regular IPv4 traffic was successfully being routed through the WireGuard tunnel during normal operation.

![WireGuard tunnel validation](/assets/images/kali-vpn-killswitch/validation-vpn-connectivity.png)

### IPv6 Leak Prevention

The WireGuard configuration used in this project defines `0.0.0.0/0` in `AllowedIPs`, routing the IPv4 default path through the Mullvad peer. It does not define an IPv6 default route through WireGuard.

During inspection of the routing configuration, an IPv6 default route through the underlying `eth0` interface was identified. This represented a potential bypass path that required explicit validation.

An IPv6 HTTPS connection was forced using `curl -6`. DNS resolution successfully returned IPv6 addresses, but the TCP connection could not be established and eventually timed out.

To determine whether IPv6 packets were reaching the underlying interface, `tcpdump` was executed on `eth0` while another forced IPv6 connection was attempted.

No TCP/IPv6 packets on port `443` were captured on `eth0`.

![IPv6 leak prevention validation](/assets/images/kali-vpn-killswitch/validation-ipv6.png)

The result is consistent with the nftables `inet` kill switch blocking unauthorized IPv6 traffic before it can leave through the underlying network interface.

This test demonstrated that the existence of an IPv6 route through `eth0` did not allow applications to bypass the VPN security policy.

### Fail-Closed Behavior

The primary fail-closed test was performed by deliberately stopping the `wg-quick@wg-mullvad` service while leaving the nftables kill switch active.

After the service was stopped, the `wg-mullvad` interface no longer existed.

The custom `inet killswitch` table remained loaded with its default-drop outbound policy, while the operating system still retained its normal IPv4 default route through the VirtualBox NAT gateway on `eth0`.

This created the condition required to test whether traffic would fall back to the underlying network connection:

* WireGuard tunnel unavailable.
* `wg-mullvad` interface unavailable.
* Default route through `eth0` still present.
* nftables kill switch still active.

An initial request using a hostname failed because DNS resolution was unavailable. To remove DNS from the test entirely, a second request was sent directly to the public IPv4 address `1.1.1.1`.

Linux routing confirmed that the destination would normally be reached through:

`eth0 → 10.0.2.2 → external network`

However, the direct connection attempt timed out.

![Fail-closed validation](/assets/images/kali-vpn-killswitch/validation-fail-closed.png)

This demonstrated an important distinction between routing and firewall enforcement: although the operating system had a valid route capable of reaching the destination through `eth0`, the nftables policy did not authorize that traffic.

The WireGuard service was subsequently restarted, the tunnel was re-established, and normal Internet connectivity returned.

The observed behavior therefore followed the intended fail-closed model:

**VPN available → connectivity available through the VPN**

**VPN unavailable → underlying route still exists, but direct Internet access remains blocked**

### DNS Leak Prevention

DNS behavior was also inspected to verify that resolver traffic was not transmitted in plaintext through the underlying interface.

The system resolver configuration contained two DNS servers:

* Mullvad DNS resolver configured by WireGuard
* An additional resolver provided by the underlying network

During a normal DNS lookup, `tcpdump` was used simultaneously on the `wg-mullvad` and `eth0` interfaces.

DNS traffic was observed on `wg-mullvad`, while no traffic on port `53` was captured on `eth0`.

![DNS leak prevention validation](/assets/images/kali-vpn-killswitch/validation-dns.png)

A second test explicitly requested DNS resolution using the resolver address associated with the underlying network. The query received a valid response, while no plaintext DNS traffic was captured on `eth0`.

This demonstrated that the explicit DNS request did not bypass the kill switch through the underlying interface. However, this test did not determine which component ultimately answered or redirected the query.

![DNS fallback validation](/assets/images/kali-vpn-killswitch/validation-dns-fallback.png)

During the performed tests:

* Standard DNS queries were observed through `wg-mullvad`.
* No plaintext DNS traffic on port `53` was observed on `eth0`.
* Explicit attempts to use the underlying resolver also did not produce DNS traffic on `eth0`.

These results demonstrate that, under the tested conditions, DNS requests remained constrained by the same fail-closed network policy applied to other outbound traffic.


## Results

The implemented environment successfully achieved the intended fail-closed networking behavior.

During normal operation, IPv4 traffic was routed through the `wg-mullvad` WireGuard interface and external connectivity remained available through the Mullvad VPN tunnel.

When the WireGuard tunnel was deliberately disabled, the virtual machine retained its underlying default route through `eth0`, but direct Internet connectivity remained blocked by the nftables outbound default-deny policy. This confirmed that loss of the VPN tunnel did not result in fallback to the regular network connection.

A potential IPv6 bypass path was also identified during routing analysis. Although the virtual machine had an IPv6 default route through `eth0`, forced IPv6 connection attempts failed, and packet capture confirmed that no TCP/IPv6 traffic reached the underlying interface during the test.

DNS traffic also remained constrained by the VPN policy. Standard DNS queries were observed through `wg-mullvad`, while no plaintext DNS traffic was captured on `eth0`. Explicit attempts to query the resolver associated with the underlying network also produced no plaintext DNS traffic on `eth0`.

The final environment therefore demonstrated the following properties:

* Regular IPv4 Internet traffic was routed through the WireGuard tunnel.
* Direct outbound Internet access through `eth0` was blocked.
* Loss of the VPN tunnel resulted in loss of external connectivity rather than traffic leakage.
* IPv6 traffic was prevented from bypassing the VPN through the underlying interface.
* Plaintext DNS traffic was not observed leaving through `eth0` during the performed tests.
* The firewall and WireGuard services were configured to persist across system boot through systemd.
* Firewall initialization occurred before the WireGuard service, preserving the fail-closed model during startup.

Overall, the implemented design met the project's primary objective: providing a Kali Linux virtual machine with outbound connectivity that remains restricted to the VPN path and fails closed when that path becomes unavailable.


## Limitations

Although the environment successfully demonstrated the intended fail-closed behavior, its security model depends on several assumptions and has important technical limitations.

### Privileged Configuration Changes

The environment assumes that users with administrative privileges will not intentionally disable or modify the implemented security controls.

Because nftables rules define which outbound paths are authorized, removing or incorrectly modifying the `killswitch` table could allow traffic to bypass the intended VPN-only policy.

For this reason, the design protects against network-path failures and unintended fallback behavior, but it does not attempt to defend against a privileged local user deliberately disabling the firewall or changing the routing configuration.

### Host and Virtualization Trust

The Kali Linux environment runs as a virtual machine inside a Windows host using VirtualBox.

The security model therefore assumes that both the host operating system and the virtualization layer remain trustworthy and uncompromised.

A compromise of the host system or a vulnerability capable of breaking the isolation provided by VirtualBox could undermine the protections implemented inside the guest virtual machine.

The project does not attempt to protect against attacks targeting the host or the virtualization platform itself.

### VPN Provider Dependency

The environment depends directly on Mullvad and the WireGuard infrastructure provided by the VPN service.

The local kill switch can prevent traffic from bypassing the configured VPN path, but it cannot protect against failures or security issues occurring inside the VPN provider's infrastructure.

Mullvad is therefore treated as a trusted component within the scope of this project.

The design also does not provide an absolute anonymity guarantee, since VPN usage alone cannot prevent application-level identification, browser fingerprinting, authenticated-account correlation, or other tracking mechanisms.

### IPv6 Connectivity

The WireGuard configuration used in this environment defines `0.0.0.0/0` as the peer's `AllowedIPs`, providing an IPv4 default route through the VPN but no equivalent `::/0` IPv6 route.

The virtual machine still receives an IPv6 route through the underlying network interface. However, the nftables `inet` kill switch prevents regular IPv6 traffic from using `eth0`.

As a result, the current design prevents IPv6 leakage by denying IPv6 connectivity outside the VPN rather than by tunneling IPv6 traffic through Mullvad.

IPv6 applications that require direct IPv6 connectivity therefore cannot operate normally in the current configuration.

### Underlying DNS Resolver

The system resolver configuration also contains a DNS server supplied by the underlying network in addition to the Mullvad DNS server.

When the VPN is active, the policy-routing configuration prevents regular DNS traffic from freely using the underlying `eth0` path.

During validation, an explicit query directed to the resolver address associated with the underlying network received a response, while no plaintext DNS traffic on port `53` was observed on `eth0`. The test therefore demonstrated that the query did not bypass the kill switch through the underlying interface, although it did not determine which component ultimately answered or redirected the request.

If the VPN becomes unavailable, the nftables default-deny policy prevents DNS traffic from falling back directly through `eth0`.

The current design therefore prevents the tested DNS fallback path from leaking through the underlying interface, while DNS availability still depends on an authorized network path remaining available.

### nftables Reload Behavior

The persistent nftables configuration begins with a `flush ruleset` directive.

During normal system startup this does not cause a conflict because nftables is loaded before `wg-quick`, allowing the WireGuard service to add its auxiliary nftables rules afterward.

However, manually reloading the nftables service while the WireGuard tunnel is already active can remove the auxiliary rules created dynamically by `wg-quick`.

The custom `killswitch` table is recreated, preserving the outbound default-deny policy, but the WireGuard networking state may become inconsistent until the WireGuard configuration is reapplied.

This represents an operational limitation of the current configuration and should be considered when modifying or reloading firewall rules.

### Scope of the Firewall

The firewall implemented in this project is primarily an outbound traffic control mechanism designed to enforce VPN-only connectivity.

The input chain remains permissive, and the project does not attempt to provide complete host hardening, malware protection, application sandboxing, or comprehensive inbound attack prevention.

The environment should therefore be considered a specialized fail-closed networking configuration rather than a complete security architecture for the virtual machine.


## Lessons Learned

This project provided significantly more learning value than the initial goal of configuring a VPN-protected Kali Linux virtual machine. Building, analyzing, and validating the environment required a deeper understanding of Linux networking, firewall behavior, routing, VPN architecture, and security design principles.

### Linux Networking and Packet Flow

One of the most valuable lessons was developing a clearer mental model of how network traffic moves through a Linux system.

Rather than treating network connectivity as a single operation, I learned to distinguish the different mechanisms involved in delivering a packet to its destination.

Applications generate network traffic, the Linux networking stack evaluates routing policies and routing tables to determine the appropriate path, and firewall rules independently enforce whether that traffic is authorized.

This distinction became especially clear during the fail-closed validation. Even when Linux still had a valid default route through `eth0`, nftables prevented the packet from using that path.

Understanding the difference between **having a route** and **having permission to use that route** was one of the most important concepts developed during the project.

### Policy Routing and Packet Marks

Before this project, I was not familiar with the use of firewall marks (`fwmark`) as packet metadata.

Analyzing the WireGuard configuration showed how Linux can associate metadata with packets and use that information when making routing decisions.

In this environment, regular Internet-bound IPv4 traffic is directed to routing table `51820` and enters the `wg-mullvad` interface. After WireGuard encrypts and encapsulates the original traffic, the resulting outer packet receives the mark `0xca6c`.

This mark allows Linux policy routing to distinguish the encrypted WireGuard packet from ordinary application traffic and prevents the packet from being recursively routed back into the VPN tunnel.

The project therefore introduced me not only to traditional routing tables, but also to **policy-based routing**, where packet characteristics can influence which routing logic is applied.

### Firewall Engineering with nftables

The project also provided practical experience designing and analyzing nftables rules instead of treating a firewall as a simple list of blocked ports.

I learned how an outbound `default-deny` policy can be used to define a small set of explicitly authorized network paths.

Rather than allowing unrestricted traffic through `eth0`, the firewall permits only the traffic required to establish and maintain the environment, including the WireGuard endpoint, DHCP traffic, loopback communication, established connections, and regular traffic through `wg-mullvad`.

This helped reinforce an important security principle:

**Access should be explicitly permitted rather than implicitly trusted.**

I also learned to distinguish the custom nftables rules implemented for the kill switch from the auxiliary rules dynamically created by `wg-quick`.

### Default Deny and Fail-Closed Design

The concepts of **default deny** and **fail closed** became practical rather than theoretical during this project.

Default deny means that traffic is blocked unless an explicit rule permits it.

Fail-closed design extends this idea to failure scenarios: when a security-critical component becomes unavailable, the system should move toward a safer state rather than silently reducing its protections.

In this environment, losing the VPN tunnel results in loss of external connectivity instead of fallback to the underlying Internet connection.

Analyzing this behavior also changed the way I approached system failures. Instead of considering only the intended network path, I began asking questions such as:

* What happens if this component fails?
* Which fallback route becomes available?
* Could another protocol bypass the intended path?
* Does a failure reduce security or only availability?

This reasoning directly led to the investigation of the IPv6 route, the underlying DNS resolver, and the direct `eth0` fallback path.

### VPNs, Encryption, and the Limits of Anonymity

Another important lesson was understanding the difference between **protecting a network path** and achieving anonymity.

WireGuard encrypts traffic between the virtual machine and the VPN endpoint and prevents the underlying network from directly observing the original traffic carried inside the tunnel.

However, this does not eliminate other forms of identification or correlation.

Authenticated accounts, cookies, browser fingerprinting, application identifiers, behavioral patterns, VPN provider trust, and traffic correlation can still expose information about a user or activity.

This project therefore helped separate concepts that are often incorrectly treated as equivalent:

**Encrypted traffic is not the same as anonymous activity.**

The kill switch reduces the risk of unintended network exposure, but it does not attempt to provide a complete anonymity system.

### Validation and Evidence-Based Troubleshooting

A major change in my approach during this project was moving from simply looking for a working configuration to trying to understand and validate each assumption.

Commands such as `ip addr`, `ip route`, `ip rule`, `wg show`, `nft list ruleset`, `systemctl`, and `tcpdump` became tools for investigating the actual state of the operating system rather than commands to execute without understanding their output.

Instead of assuming that IPv6 was protected, I inspected the routing table, identified a possible bypass path, forced an IPv6 connection, and observed the underlying interface with `tcpdump`.

Instead of assuming that DNS could not leak, I captured DNS traffic on both the VPN and underlying interfaces and explicitly attempted to use the resolver provided by the local network.

Instead of assuming that the kill switch worked, I disabled WireGuard while preserving the normal `eth0` route and attempted to establish a direct connection to a public IP address.

This process reinforced an important security mindset:

**A security property should be tested whenever possible rather than assumed from configuration alone.**

### System Initialization and Configuration Persistence

Investigating persistence also introduced me to how systemd controls service initialization and dependencies.

I learned that having two services enabled at boot is not enough to guarantee a secure startup sequence. Their ordering also matters.

By examining the nftables and `wg-quick` service definitions, I was able to understand why the firewall is loaded before the normal network initialization process while WireGuard is started only after the underlying network becomes available.

This showed how security behavior can depend not only on configuration files, but also on **when and in which order those configurations are applied**.

### Virtualization and Network Abstraction

Configuring the Kali Linux virtual machine also improved my understanding of how multiple network abstraction layers interact.

The project required distinguishing between the logical WireGuard interface, Kali's virtual Ethernet interface, VirtualBox NAT, the Windows host network stack, the physical network interface, and the external VPN endpoint.

Understanding these layers made it easier to reason about how an encrypted WireGuard packet can logically belong to the VPN while still physically travelling through `eth0` and the host's network connection.

Overall, the project transformed several networking and security concepts from abstract terminology into mechanisms that I could inspect, test, and explain through the behavior of a real system.
